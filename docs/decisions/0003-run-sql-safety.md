# 0003. run_sql 안전장치: 검사는 안내, 방어는 DB

- 상태: 채택 (2026-10-30). ADR 0001 결정 4의 구현.
- 구현: `src/inhouse/agent/sqlguard.py`, `runner.py`, `audit.py` · 테스트 `tests/test_sqlguard.py`(3), `tests/test_runner_db.py`(9)

## 결정

1. **SQL 검사(sqlglot)는 방어선이 아니라 안내 층**이다. 실행해 봤자 DB가 거절할 SQL을 미리 걸러, 모델이 고칠 수 있는 이유를 한국어로 돌려준다
   ("함수 set_config()는 쓸 수 없습니다", "시스템 카탈로그는 탐색 도구로 확인하세요").
   파서는 모르는 구문을 그냥 `Command`로 읽거나(`SET ROLE`, `EXPLAIN`), 이상하게 읽는다(`LISTEN x` → 별칭).
   그래서 **루트는 SELECT/집합 연산만 허용**하고, 나머지는 트리 전체를 돌며 쓰기 구문·`INTO`·`FOR UPDATE`·위험 함수·카탈로그를 거절한다.
2. **방어는 DB**: 묻는 직원의 역할로 접속(ADR 0002) → 읽기 전용 트랜잭션 → `SET LOCAL statement_timeout`.
   역할 기본값에도 같은 값이 있지만, runner가 직접 건다 (테스트는 역할 기본값을 끈 상태에서 확인).
3. **SQL을 고쳐 쓰지 않는다**: 결과 크기는 `LIMIT`을 덧붙이지 않고 서버 쪽 커서로 상한+1행만 가져와 막는다.
   `LIMIT` 덧붙이기는 `ORDER BY`·집합 연산·이미 있는 `LIMIT`과 얽혀 뜻을 바꿀 수 있다. 상한을 넘으면 `truncated: true`.
4. **거절·오류·타임아웃도 전부 감사 로그**(JSONL 한 줄 = 한 실행). 결과마다 쿼리 ID(`q-YYYYMMDD-xxxxxxxx`) — 답의 출처가 이 ID를 가리킨다.
   DB 오류 메시지(권한 없음·없는 열)는 모델에게 그대로 돌려 고쳐 쓰게 한다.

## 테스트가 잡는지 확인한 변형

runner에서 읽기 전용 빼기 · 타임아웃 빼기 · 상한까지만이 아니라 전부 가져오기 · 검사 건너뛰기 → 모두 실패로 잡힘.
처음엔 "전부 가져오기"를 못 잡아서(결과가 같아 보임) 끝나지 않는 재귀 쿼리 테스트를 추가했다:
상한까지만 가져오면 즉시 끝나고, 전부 가져오려 하면 타임아웃.

## 알게 된 것

- DB 역할은 클러스터 전체에 하나다. 같은 클러스터에서 통합 테스트를 돌리면 직원 역할 비밀번호가 테스트 값으로 바뀐다.
  → 테스트는 별도 클러스터(CI는 서비스 컨테이너)에서, 로컬에선 테스트 후 `load`를 다시 돌리거나 비밀번호를 같게.
- 콜드 캐시 첫 쿼리는 RLS 하위 조회 때문에 1.6초까지 걸렸다 (따뜻하면 0.1초). 타임아웃 5초 안이지만 웹 화면에선 첫 질문이 느릴 수 있다.
