# 0004. 2단계: 사내 문서 검색 + 쓰기 작업 승인 흐름 (CS 환불 처리)

- 상태: 채택 (2026-11-04, 호열과 합의 — 결정 6개 모두 추천안대로)
- 앞선 결정: [0001](0001-inhouse-sql-agent.md) 1단계 SQL · [0002](0002-permission-model.md) 권한 · [0003](0003-run-sql-safety.md) run_sql 안전장치

## 배경

1단계 에이전트는 **조회만** 하고 근거는 **DB 숫자뿐**이다. 실제 사내 업무는 규정 문서를 읽고 판단해서 무언가를 **바꾼다**.
가상 고객사 Tucanova의 CS팀장 인터뷰를 가정하면: 환불 문의마다 상담원이 규정 문서(여러 번 개정됨)를 찾아 읽고,
주문·배송 기록을 확인하고, 팀장에게 메신저로 승인을 받아 수기로 환불을 넣는다. 규정을 옛 버전으로 읽는 실수와
승인 없이 넣은 환불이 감사에서 지적됐다.

## 결정

1. **범위: 한 업무 흐름으로 묶는다 — CS 환불 처리.**
   "주문 X 환불 돼?" → 에이전트가 환불 규정 문서를 찾고(문서 검색) 주문·배송 기록을 조회(SQL) →
   규정에 맞으면 환불을 **제안** → 팀장이 승인 → 시스템이 실행. 만드는 순서는 **2a 문서 검색 → 2b 승인 흐름**.
2. **문서: 가상 사내 문서를 직접 쓴다 (약 30개, 한국어).** 환불·반품 규정, 배송 기준, CS 응대 지침, 권역 운영 공지, 지표 회의록, 인사·보안 문서.
   DB처럼 **함정을 일부러 넣고 문서화**한다 (`docs/doc-notes.md`):
   개정 전·후 버전 공존(시행일로 골라야 함) · 본사 규정과 권역 공지의 충돌(우선순위 규칙) · 권한 밖 문서 · 같은 뜻 다른 단어(반품/환불/취소).
   실존 회사 규정을 베끼지 않는다.
3. **검색: Postgres 안의 키워드 검색으로 시작, 측정 후 필요하면 임베딩을 더한다.**
   문서 조각을 표에 넣고 전문 검색(tsvector, 한국어는 2글자 단위로 쪼개 `simple` 설정, `ts_rank`)으로 점수를 낸다.
   추가 키·서버가 없고 권한을 DB가 그대로 거른다. 검색 정답셋에서 재현율이 목표에 못 미치면 그때 pgvector + 임베딩 API를 별도 결정으로 붙인다.
4. **문서 권한도 DB가 거른다.** 문서 조각 표에 1단계와 같은 `session_user` 기준 행 단위 보안을 건다 (부서·권역별 열람 범위).
   앱 코드가 검색 결과를 거르지 않는다 — 걸러내는 코드의 버그 하나가 곧 유출이기 때문.
5. **출처: 문서 ID · 절 · 시행일, 그리고 코드가 확인한다.** 에이전트가 인용한 문장이 실제로 그 조각에 있는지,
   인용한 버전이 질문 시점에 시행 중인지 코드가 검사해 결과에 붙인다. 숫자의 쿼리 ID와 같은 원칙을 문서로 넓힌 것.
6. **쓰기: 에이전트는 실행 권한이 없고 제안만 한다.**
   - 에이전트 DB 역할은 지금처럼 읽기 전용. 추가로 허용하는 건 `propose_refund(...)` 함수 실행 하나 (SECURITY DEFINER).
     이 함수가 규정 검사(금액 ≤ 품목 판매가 − 이미 환불한 금액, 기간, 주문 상태, 권역)를 DB 안에서 하고 `대기` 제안 한 줄만 만든다.
   - 승인은 **사람이** 웹 화면에서: 제안자 ≠ 승인자, 역할별 승인 한도(CS 팀장 · 권역 매니저 · 본사), 만료 시각.
   - 실행은 승인된 제안만, 같은 제안은 한 번만 반영(멱등). 제안·승인·거절·실행을 전부 감사 기록으로.
   - 테스트가 직접 시도해 막히는지 본다: 에이전트의 직접 INSERT/UPDATE · 자기 제안 자기 승인 · 한도 초과 · 권역 밖 주문 · 두 번 실행 · 만료 후 승인.

## 측정 (목표는 첫 측정 후 조정)

| 기준 | 목표 |
|---|---|
| 문서 검색 재현율 (정답 조각이 상위 5개 안) | 90% 이상 |
| 문서 질문 정확도 (옛 버전·충돌 함정 포함) | 80% 이상 |
| 인용 검증 통과 (인용 문장이 실제 조각에 있음) | 맞은 답의 95% 이상 |
| 권한 밖 문서 노출 | 0건 |
| 에이전트의 직접 실행 | 0건 (제안만) |
| 환불 제안 정확도 (금액·가부) | 80% 이상 |

정답셋에 약 30문항 추가: 문서 질문 · 문서 + SQL 혼합 · 환불 제안(맞는 금액, 규정 밖이면 거절) · 권한 밖 문서 요청.
1단계처럼 정답은 사람이 검토하고, 문서의 함정 목록과 문항을 연결한다.

## 순서

- **2a-1** CS팀장 인터뷰 요구사항(`docs/customer-brief.md`에 2단계 절) · 문서 약 30개 · 함정 목록 `docs/doc-notes.md`
- **2a-2** 문서 표 + 조각 나누기 + 행 단위 보안 + 적재 · 권한 테스트(우회 시도 포함, 정책 변형을 테스트가 잡는지)
- **2a-3** `search_docs` 도구 + 인용 검증 + 테스트
- **2a-4** 검색 정답셋으로 재현율 측정 → 문서 질문 정답셋 · 에이전트 측정
- **2b-1** 제안·승인 표와 함수, 승인자 역할 · 우회 테스트 · 변형 확인
- **2b-2** `propose_refund` 도구 + 웹 승인 화면(대기 목록 · 승인/거절 · 감사)
- **2b-3** 환불 제안 정답셋 · 측정 · 라이브 확인
- **2b-4** 공개 데모에서 승인을 열지 결정(연다면 매일 초기화되는 연습용 데이터) · README 사례 연구에 2단계

## 하지 않는 것

- 에이전트가 환불을 직접 실행하는 경로 (승인 생략 옵션 포함)
- 임베딩 검색을 측정 전에 먼저 넣기
- 실제 결제 시스템 연동 (환불 "실행" = 사내 DB의 환불 기록 생성까지)

## 2b-1 구현 (2026-11-04)

- 승인권자 두 명을 직원 표에 더했다: 본사 운영책임자 `u_e002`(HQ_OPS), CS 팀장 `u_e203`(CS_LEAD). 이름은 ORG-001 문서와 같고, 난수를 쓰지 않아 기존 데이터는 그대로다.
- 표: `rfnd_req`(제안: 대기 → 실행·거절·만료), `apr_limit`(승인일 기준 한도, POL-APR-001 두 판). 환불 번호는 시퀀스.
- 직원 역할의 쓰기 권한은 여전히 0. 쓰기는 SECURITY DEFINER 함수 두 개로만:
  - `propose_refund(주문, 사유, 금액, 근거)` — CS 담당·CS 팀장만. 배송 완료·테스트 아님·사유 DMG/WRONG/LATE·근거 필수·같은 주문 같은 사유 한 번·
    **남은 한도 = 품목+배송비 − 이미 환불 − 대기 중 제안**. 주문 행을 잠가 제안을 한 줄로 세운다.
  - `decide_refund(제안, 승인 여부, 메모)` — CS 팀장·권역 매니저(고객 주소 기준 자기 권역)·본사 운영책임자만. 본인 제안 불가, 72시간 만료, 거절은 사유 필수,
    승인일(현지)의 한도. 승인하면 같은 트랜잭션에서 환불 기록을 만들고 `executed`로 바꾼다 (승인과 실행을 나누지 않아 "승인됐는데 실행 안 됨"이 없다).
    제안 행을 `FOR UPDATE`로 잠가 동시에 두 번 승인해도 한 번만 실행된다.
- 에이전트의 `run_sql`은 읽기 전용 트랜잭션이라 두 함수 모두 실행되지 않는다 (테스트로 확인). 함수의 PUBLIC 실행 권한은 뺐다.
- 규정상 금액(사유별 계산·기한)은 DB가 강제하지 않는다 — 판단은 제안 근거와 승인권자의 몫이고, DB는 넘으면 안 되는 선(한도·권한·중복·상태)만 막는다.
  신청 기한도 DB가 막지 않는다: 이 데이터의 "지금"(2026)이 주문 시기(2016~2018)와 달라 의미가 없어서다.
- 테스트 14개. 검사를 하나씩 뺀 변형 14개를 모두 잡는다. 처음엔 2개가 살아남았다 — 승인자 역할 검사를 빼도 한도표에 줄이 없어 막혔고,
  환불 표 쓰기 권한을 줘도 RLS에 쓰기 정책이 없어 막혔다. 다른 층이 대신 막은 것이라, 거절 이유와 권한 자체를 따로 확인하게 테스트를 조였다.
