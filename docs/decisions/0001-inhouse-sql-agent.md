# 0001. 가상 고객사 사내 데이터 에이전트 — 1단계: SQL

- 상태: **채택** (2026-10-30, 사용자 합의). 이커머스 · **공개 데이터셋(Olist) 중심 + 일부 합성** · PostgreSQL · 탐색 도구 + 지표 사전 · 웹 먼저.
  가상 고객사 이름은 **Tucanova**. 선택지 표는 결정 당시 비교 기록으로 남긴다.
- 범위: 1단계는 **사내 DB에 자연어로 묻고, 권한 안에서, 출처(실행한 SQL)와 함께 답하는 것**까지.
  문서 RAG·쓰기 작업 승인 흐름은 2단계(별도 ADR).

## 맥락

- 지금 포트폴리오(stat/corp/air/realty/trend-agent, korea-data-mcp)는 전부 **공개 데이터 · 조회 전용 · 사용자 한 명**이다.
  FDE가 실제로 하는 일은 고객사 **내부** 데이터, **권한**, **지저분한 스키마**, 고객마다 다른 **지표 정의**를 다루는 것이고, 여기가 빈칸이다.
- 그래서 가상 고객사 하나를 만들어 "고객 온보딩 → 스키마 파악 → 지표 정의 합의 → 안전하게 연결 → 정확도 측정"을 한 번 끝까지 해 본다.
- 이전 프로젝트의 원칙은 그대로 옮긴다:
  - 출처 없는 숫자는 없다 → **답의 숫자마다 그 숫자를 만든 SQL(쿼리 ID)과 실행 시각**
  - 계산은 모델이 암산하지 않는다 → **집계·비율은 SQL이 하고, 모델은 결과 행을 다시 계산하지 않는다**
  - 고정 정답셋으로 정확도를 측정한다 → **정답 SQL 대비 실행 결과 일치율**

### 2. 데이터를 어떻게 만드나

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| a | 직접 만든 합성 데이터 (시드 고정 생성 스크립트) | 한국 맥락, 일부러 넣은 "함정"을 문서화해 정답셋과 연결 가능. 재현 가능 | 생성 규칙을 직접 설계해야 함 |
| b | **공개 이커머스 데이터셋 (Olist) — 채택(+ a 일부)** | 진짜 데이터의 지저분함 | 해외 데이터, 라이선스 확인 필요, 함정을 내가 통제 못 함 |

- 결정은 **b 중심 + a 일부** (아래 "결정" 2번). 원래 추천은 a였지만, 실제 데이터의 지저분함(사람이 만든 함정이 아닌 진짜 함정)이 더 설득력 있다는 판단.
- 합성 쪽에서 **일부러 넣는 함정** 후보 (실제 사내 DB에서 흔한 것들, 정답셋 문항과 1:1로 연결):
  - 주문 상태가 코드 값(`status_cd` 10/20/30/90)이고 뜻은 코드 테이블에만 있음
  - 부분 환불은 별도 `refunds` 테이블 → "매출"에서 빼야 함
  - 테스트 주문(`is_test`)과 탈퇴 고객(`deleted_at`)이 섞여 있음
  - 시각은 UTC로 저장 → "어제 매출"은 KST 날짜로 잘라야 함
  - 옛 테이블 하나는 금액이 천원 단위
  - 컬럼명 약어(`cust_no`, `ord_amt`, `dlv_fee`)

### 3. DB

| | DB | 장점 | 단점 |
|---|---|---|---|
| ① | **PostgreSQL 16 (Docker)** | 행 단위 보안(RLS), 읽기 전용 역할, `statement_timeout` — 권한을 DB가 강제 | 띄울 게 하나 늘어남 |
| ② | SQLite | 파일 하나 | RLS·역할 없음 → 권한을 앱 코드로 흉내 내야 함 |
| ③ | DuckDB | 분석 쿼리 빠름 | 사내 운영 DB 느낌이 아님, 권한 모델 약함 |

- 추천 **①**. 권한을 "프롬프트로 부탁"이 아니라 **DB가 거절**하게 만드는 게 이 프로젝트의 핵심이다.

### 4. SQL 안전장치 (선택지가 아니라 전부 넣음, 겹겹이)

1. **DB 역할**: 에이전트 전용 읽기 전용 역할, 필요한 뷰/테이블에만 `SELECT` 권한. 이게 진짜 방어선.
2. **읽기 전용 트랜잭션** + `statement_timeout`(예: 5초) + 결과 행 수 상한(예: 500행, 넘으면 잘렸다고 알림).
3. **SQL 파서 검사** (sqlglot): 문장 하나, `SELECT`/`WITH`만, 시스템 카탈로그 접근 금지.
   목적은 방어보다 **모델에게 친절한 에러 메시지**(왜 거절됐는지 알려 고쳐 쓰게).
4. **감사 로그**: 누가·무슨 질문으로·어떤 SQL을·몇 행·몇 ms. 답의 출처(쿼리 ID)가 이 로그를 가리킨다.

### 5. 모델에게 스키마·지표를 어떻게 알려주나

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| ㄱ | 전체 스키마를 프롬프트에 | 단순 | 테이블이 늘면 토큰·혼동 증가, 함정 설명이 묻힘 |
| ㄴ | **탐색 도구** (`list_tables`, `describe_table`(컬럼 설명·예시 값), `run_sql`) | 필요한 것만 봄, 기존 에이전트와 같은 tool-use 패턴 | 왕복 증가 |
| ㄷ | **지표 사전** (`lookup_metric`: "매출 = 결제 완료 − 환불, 테스트 주문 제외, KST 기준") | 고객마다 다른 단어 뜻을 코드로 고정. FDE 온보딩의 핵심 산출물 | 사전을 고객과 "합의"하는 과정을 문서로 남겨야 함 |

- 추천 **ㄴ + ㄷ**. 지표 사전은 YAML로 레포에 두고, 정의마다 "가상 고객 담당자와 합의한 날짜·이유"를 적는다.

### 6. 권한

| | 방식 | 판단 |
|---|---|---|
| 가 | **PostgreSQL RLS + 요청마다 세션 변수로 사용자 지정** (`SET app.user_id`) | 추천. 모델이 WHERE를 빼먹어도 DB가 막는다 |
| 나 | 앱이 SQL에 WHERE를 덧붙임 | 기각. SQL 재작성은 깨지기 쉽고 우회 가능 |
| 다 | 프롬프트로 "자기 지역만 조회하라" | 기각. 권한이 아니라 부탁 |

- 가상 사용자 3명: **본사 분석가**(전체), **지역 매니저**(자기 지역 행만 — RLS), **CS 담당**(전화번호·이메일 마스킹 — 컬럼 권한 + 마스킹 뷰).
- 데모 화면에 **사용자 전환** 스위치를 두어 같은 질문에 답이 달라지는 걸 보여준다.

### 7. 평가

- 정답셋 **50문항**, 각 문항에 정답 SQL. 구성 예: 단순 조회 10 · 조인 10 · 지표 정의 10 · 함정 10 · 권한 10.
  **정답 SQL은 직접 쓴다** (이게 SQL 공부: JOIN, CTE, 윈도 함수, 날짜·시간대).
- 지표:
  - **실행 정확도**: 에이전트 SQL 결과 = 정답 SQL 결과 (행 순서 무시, 수치는 허용 오차)
  - **권한 위반 0건** (지역 매니저가 다른 지역 숫자를 받으면 실패) — 정확도와 별개의 필수 조건
  - **위험 SQL 차단 100%** (쓰기·다중 문장·카탈로그 접근을 유도하는 질문)
  - 문항당 비용·지연
- Haiku 5.5 기본, Sonnet 5.5와 같은 정답셋으로 비교해 "정확도 vs 비용" 표를 남긴다.

### 9. 엔지니어링 기본기 (처음부터)

- **Docker Compose**: `postgres` + `app` + 시드 데이터 적재. `docker compose up` 하나로 재현.
- **CI (GitHub Actions)**: Postgres 서비스 컨테이너로 오프라인 테스트(안전장치·RLS·지표 사전·파서). LLM 정답셋 평가는 비용이 들어 수동 실행, 결과 파일을 커밋.
- **관측**: 요청 하나당 구조화 로그(JSON) 한 줄 — 사용자, 질문, 도구 호출, SQL, 행 수, 지연, 토큰, 비용. 화면에서 "이 답의 SQL 보기".
- **비용 상한**: trend-agent처럼 하루 Claude 비용 상한.

## 구현 순서 (테스트 먼저) — 1 완료

1. `docs/customer-brief.md` → Olist 내려받기(해시 확인)·적재 + 합성 덧층(시드 고정) + 스키마·함정 목록 → Docker Compose
2. DB 역할·RLS·마스킹 뷰 + 테스트 (지역 매니저로 다른 지역 조회 → 0행, CS로 전화번호 → 마스킹)
3. `run_sql` 안전장치(파서·읽기 전용·타임아웃·행 상한·감사 로그) + 테스트 (쓰기·다중 문장 거절)
4. 지표 사전 + `list_tables`/`describe_table`/`lookup_metric` 도구
5. 정답셋 50문항 (정답 SQL 직접 작성) + 평가 스크립트 → Haiku/Sonnet 첫 측정
6. 웹 화면 (사용자 전환, 답·SQL·감사 로그) → CI → showcase 카드
